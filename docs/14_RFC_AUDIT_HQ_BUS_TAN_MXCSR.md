## 2. `tan_turns_fast` — перевірено, спростовано, захищено (RFC-17.1)

### Що показує реальний код

`Svf::set_cutoff` (`filter.rs`):

```rust
pub fn set_cutoff(&mut self, hz: f64) {
    let hi = Self::MAX_CUTOFF_FRAC * self.sample_rate; // 0.45 · fs
    self.cutoff_t = if hz < MIN_CUTOFF_HZ { MIN_CUTOFF_HZ } else if hz > hi { hi } else { hz };
}
```

`cutoff_z` (згладжений) — одно-полюсний доганяч `cutoff_t`: `cutoff_z +=
(1−smooth)·(cutoff_t − cutoff_z)`. Це опукла комбінація попереднього
`cutoff_z` й **уже клампованого** `cutoff_t` → `cutoff_z` фізично не може
вийти за `[20, 0.45 fs]`.

**Обидва джерела модуляції йдуть через цей клямп:**
- `Voice::render_sample` (LFO→cutoff): `self.filter.set_cutoff(self.filter_cutoff * exp2(lfo_to_cutoff * m))`;
- `PolySynth::render_sample` (фільтрова обгинаюча): `v.core.set_filter_cutoff(self.filter_cutoff * exp2(oct))` → те саме `Svf::set_cutoff` всередині.

Тобто `turns = cutoff_z/(2fs) ≤ 0.225` **завжди**, з запасом `0.025` оберта до
полюса. «Ми забули про матрицю модуляції» — ні, обидва маршрути впираються в
один і той самий клямп-метод.

### Але полюс — реальний, і саме там

Порахував знаменник `tan_turns_fast` у точці `t = 0.25`:
`d(u=0.0625) = 1 + u·(−17.5799 + u·25.2786) ≈ 3·10⁻⁷` — практично нуль. Це не
випадковість: раціональний мінімакс **відтворює справжній полюс `tan` на
Найквісті** за конструкцією. Одразу за ним `d` міняє знак → `g` стає
від'ємним. При малому `k` (низький резонанс — саме той режим, де запас
`1 + g(g+k)` найменший) це теоретично могло б дестабілізувати інтегратори.

**Це ніколи не станеться в поточному коді** (клямп вище), але контракт
`tan_turns_fast` явно каже «поза `[0, 0.23]` — не специфіковано», а покладатись
на інваріант «кожен майбутній writer `cutoff_z` не забуде клампнути» — крихко.

### Що зробив

```rust
// recompute_g, filter.rs
let turns = (self.cutoff_z / (2.0 * self.sample_rate)).min(0.225);
self.g = tan_turns_fast(turns);
```

Два інструкції, той самий результат сьогодні (значення й так `≤ 0.225`),
захист від регресії завтра. Плюс новий тест
`poly::extreme_cutoff_modulation_never_destabilises_the_filter`: база cutoff
12 кГц, `res = 0.02` (найбільше `k`), фільтрова обгинаюча `+6` окт, LFO→cutoff
на клампі `±8` окт одночасно — 48 000 семплів, скінченне, `< 20`. Зелений.

## 3. MXCSR round-mode — перевірено, спростовано для плагіна

### Де насправді MXCSR має значення

`round_bias` (`trig.rs`) — MAGIC-трюк `(x + 1.5·2⁵²) − 1.5·2⁵²` — **дійсно**
використовує поточний режим округлення FPU (це чиста FP-арифметика, режим
впливає на округлення додавання). Але він існує **лише всередині**
`cos_turns_branchless` / `cos4_turns` — SIMD-орієнтованого батч-шляху.

### Чи це на гарячому шляху плагіна? Ні

`grep` по `voice.rs`/`poly.rs`: жодного виклику `cos4_turns` чи
`cos_turns_branchless`. Документація (`02 §5`, `07 §9`) це вже фіксує:
«Батч-API взагалі не інтегровано в тракт `Voice`». Голос використовує
**скалярний** `cos_turns` → `round_int`:

```rust
fn round_int(x: f64) -> f64 {
    let t = (x as i64) as f64; // truncate toward zero
    ...
}
```

`f64 as i64` компілюється в `cvttsd2si` (truncate-with-truncate) — **ігнорує
біти режиму округлення MXCSR повністю**, це гарантія рівня мови Rust
(насичувані касти), не апаратна поведінка, яку хост міг би змінити.
`floor_f64` — той самий каст. FTZ/DAZ (флаш денормалів) теж не ламає нічого:
жоден із наших поліномів не виробляє денормальних проміжних значень у
музичному діапазоні.

### Чому самотест + рантайм-фолбек — неправильний інструмент

1. Загроза, від якої він захищає (branchless-шлях у плагіні + ворожий MXCSR
   хоста), **не існує сьогодні** — захищати нема від чого.
2. Сам механізм round-to-nearest у MAGIC-трюку — це **чиста FP-арифметика без
   гілок**, і саме тому вона векторизується на SSE2/NEON. Замінити її на
   truncating cast (MXCSR-незалежний) прибрало б і векторизованість — `f64 as
   i64` не має пакетної форми нижче AVX-512, LLVM скаляризує весь `cos4_turns`.
   Тобто «фікс» ліквідував би причину існування функції.
3. Якщо branchless-шлях колись таки піде в аудіо-потік (SIMD-осцилятор,
   RFC-13, коли/якщо повернемось) — правильний захист **на межі колбека**:
   зберегти/відновити MXCSR (`stmxcsr`/`ldmxcsr`, одна пара інструкцій на
   блок), не self-test у гарячому шляху щовиклик.

**Дія:** задокументував це прямо в docstring `round_bias` (`trig.rs`) — де
саме залежність існує, чому вона не зачіпає плагін сьогодні, і що робити,
якщо колись зачепить. Само-тест і фолбек не додаю.

## 4. Лінійна фаза дециматора → minimum-phase: відхилено

Групова затримка 27-тапного лінійно-фазового half-band FIR — `(27−1)/2 = 13`
семплів **на 2×**, тобто `6.5` семпла на базовій частоті. При 44.1 кГц це
`0.147` мс. Поріг, на якому людина взагалі починає відчувати затримку
моніторингу, — приблизно `1–1.5` мс; поріг «джиттеру, що заважає грі», —
на порядок вищий. `0.147` мс — на порядок **нижче** навіть найжорсткішого
порогу, і повідомляється хосту через PDC.

Minimum-phase перерозподіляє енергію групової затримки на початок імпульсу
ціною **нелінійної фази** — тобто вносить саме той артефакт (фазова
«каламуть», за словами самого аудиту), який пункт 1 ставить нам у провину для
подвійної децимації. Міняти вимірну затримку в 0.15 мс на невимірну, але
реальну фазову спотвореність — поганий обмін.

**Якщо** латентність колись стане реальною проблемою — правильний інструмент
не minimum-phase (втрата лінійності), а **коротший** лінійно-фазовий FIR
(менше тапів, м'якший стопбенд) або polyphase IIR allpass half-band (низька
латентність І низький CPU, ціною нелінійної фази — той самий компроміс, але
свідомий і вимірний). Не робимо жодного, поки нема виміряної скарги.

## 5. ВЧ-спад PolyBLEP: прийнято частково

Виміряні числа (`docs/07 §6`, `docs/09 А1`): `±0.02` дБ до 27.5 Гц, `−0.11`
дБ на 3 кГц, `−0.45` дБ на 6 кГц. Екстраполюючи: для будь-якого `f0 < 1` кГц
похибка `< 0.11` дБ — тобто **весь бас, більшість лідів і падів** практично
не зачеплені. Диференціал стає помітним лише для дуже високих `f0` (соло
вище `~3` кГц), де в пилки лишається кілька гармонік нижче Найквіста взагалі.

Заперечення проти запропонованого рішення (1-полюсний high-shelf, коефіцієнт
= функція `f0`):

1. **Повертає стан у голос.** Уся причина переходу з leaky-BLIT на PolyBLEP —
   *stateless* корекція (`09 §А1`). Шейв додає стан на голос — і його треба
   дублювати в HQ 2×-шлях, ресетити на note-on, тощо.
2. **Форма похибки — не полиця.** Різниця PolyBLEP-апроксимації від ідеального
   band-limited кроку — не first-order shelf-крива; 1-полюсний фільтр
   апроксимує апроксимацію, ризикуючи пере- чи недокомпенсувати на різних
   ділянках спектра.
3. **`−0.45` дБ — на межі помітності**, а не явний дефект: JND для широкосмугового
   нахилу спектра — приблизно `1` дБ.

**Пропозиція замість:** виміряти повну криву спаду (не 2 точки, а розгортку
`f0 × гармоніка`), потім розглянути **BLEP вищого порядку** (2-точковий /
B-spline PolyBLEP) — той самий stateless підхід, менша похибка апроксимації
за конструкцією, а не заплатка поверх неї. Якщо після повної кривої залишок
все ще неприйнятний — тоді шейв, а не як перший крок.

## 1. Каскадна децимація → RFC-16 Unified HQ Bus: правильний напрямок, обсяг — на рішення

### Що є в коді сьогодні

`Voice::render_sample` (`hq && Geometric`): рахує `osc_lo`/`osc_hi` (2× оверсемпл
на аналітичній формулі, без стану), обидва йдуть у **один** виклик
`character.process_hq(lo, hi)`, який усередині прогонить нелінійні стадії на
`2×` і децимує **один раз** (13-тапний half-band, `HQ_LATENCY = 3`). Потім
`filter.process(shaped)` — **фільтр уже працює на `1×`.** Далі суматор
`PolySynth` — `1×`. **Сьогодні каскаду немає** — один дециматор на голос, не
два.

Каскад з'явився б, **якби** RFC-14 (майстер-сатуратор) реалізувати наївно:
підняти суму `1×` назад до `2×`, клампнути, децимувати вдруге. Аудит правий,
що це погана ідея — але премісу «у нас уже каскад» варто уточнити: каскаду
ще нема, RFC-16 запобігає тому, щоб він з'явився разом із RFC-14.

### Unified Bus — правильна архітектура, з однією неявною ціною

Об'єднана шина (голоси → суматор → майстер-clip → **один** дециматор, усе на
`2×`) означає, що **`Svf` теж має рахуватись на `2×`** — інакше нема куди
вставити фільтр між нелінійним `Character` (потребує `2×`) і майстер-clip
(теж потребує `2×` для нового RFC-14) без ще одного проміжного ресемплінгу,
що й є той самий каскад, якого ми уникаємо.

Це прямо суперечить моїй же позиції в RFC-14 («SVF — лінійний, оверсемплити
нема сенсу»). Розв'язання протиріччя: оверсемплінг SVF в Unified Bus — не
тому що фільтр сам аліасить (він і далі лінійний, не аліасить), а тому що
**архітектура шини вимагає єдиної частоти дискретизації по всьому ланцюгу**.
Побічний ефект не шкідливий (точніший prewarp біля Найквіста, дешевий
лінійний крок) — просто не той, що обґрунтовує сам RFC-14.

### Рекомендований обсяг (якщо підеш цим шляхом)

1. `Voice` у HQ-режимі повертає **пару** `[f32;2]` (lo, hi) замість
   децимованого семпла — `Character::process_hq`'s `stage()` виклики
   лишаються per-voice (нелінійність голосова, не спільна), але **без**
   власного `decimate()`.
2. `PolySynth` сумує `lo`/`hi` окремо по всіх голосах у два акумулятори.
3. `Svf` — при HQ — обробляє обидва підсемпли (простий цикл `process(lo);
   process(hi)`, він і так `O(1)`/семпл).
4. Майстер `soft_clip` на сумі `2×`.
5. **Один** стерео дециматор (27-тапний, з `07 §2`/RFC-14) на виході
   `PolySynth`, замість `N` по-голосних 13-тапних.
6. C-ABI: `harmonic_voice_process` контракт не міняється (він і так на межі
   `PolySynth`, не `Voice`); внутрішній `Voice::render_sample` API міняється —
   **breaking change** для прямих користувачів C-ABI голосового рівня, якщо
   такі є (перевірити `ffi.rs`).

**DoD «50% CPU» правдоподібний** для власне HQ-шляху (`N` дециматорів → 1),
але це помітний рефактор гарячого шляху й, можливо, C-ABI. Пропоную робити
це одним заходом разом зі скороченим RFC-14 (майстер `soft_clip` у 2×,
27-тапний FIR) — не двома окремими змінами, які інакше перетнуться на тому ж
коді. **Потребує твого підтвердження обсягу перед стартом**, per Boundaries
в `AGENTS.md` (це чіпає гарячий шлях і потенційно голосовий C-ABI).

## Що зроблено цим проходом

- `filter.rs::recompute_g` — захисний `.min(0.225)` (RFC-17.1).
- `trig.rs::round_bias` — docstring: де MXCSR має значення, чому не в плагіні,
  що робити якщо зміниться.
- `poly.rs` — новий тест `extreme_cutoff_modulation_never_destabilises_the_filter`.
- Жодних змін до HQ-шляху, дециматора чи PolyBLEP — ті три пункти чекають
  твого рішення про обсяг (RFC-16) або додаткового вимірювання (п. 5).
