## Спростовано: `.min()` і `no_std`

### Претензія
`02_NUMERICAL_METHODS.md §7` забороняє `f64::min`, і мій `.min(0.225)` у
`Svf::recompute_g` (RFC-17.1) нібито порушує це.

### Перевірка — не аргументом, а компіляцією

Мінімальний `#![no_std] #![no_main]` бінарник під `thumbv6m-none-eabi`
(Cortex-M0, **без FPU** — найсуворіший з наших чотирьох цільових таргетів,
де навіть `f64`-арифметика програмна):

```rust
#![no_std]
#![no_main]
#[panic_handler] fn panic(_: &core::panic::PanicInfo) -> ! { loop {} }
#[no_mangle]
pub extern "C" fn _start() -> ! {
    let (a, b): (f64, f64) = (1.7, 2.3);
    let out = a.min(b) + a.max(b) + a.clamp(0.0, 1.0) + a.abs();
    unsafe { core::ptr::write_volatile(0x2000_0000 as *mut f64, out); }
    loop {}
}
```

**Компілюється й лінкується чисто** (не rlib-перевірка, а повний бінарник —
якби потрібен був зовнішній `libm`-символ, лінкер впав би, бо для цього
таргету немає ні `std`, ні `libm`, ні лінкер-скрипта, що міг би його
задовольнити). Та сама проба з `a.sqrt()` замість `.min()` — **навіть не
компілюється**: `error[E0599]: no method named 'sqrt' found for type 'f64'`.
Це остаточний доказ: `sqrt` як метод **не існує** без `std` (не питання
лінкування — сам метод не в scope), а `min`/`max`/`clamp`/`abs` **є** в
`core` і компілюються в одну апаратну інструкцію (`MINSD`/`MAXSD`/`ANDPD`
тощо), без жодного символу `libm`.

Повний прогін по всьому забороненому списку (той самий метод — спроба
скомпілювати кожен метод окремо в `#![no_std]` крейті):

| Метод | `core`-safe? |
|---|---|
| `sin, cos, tan, asin, acos, atan, exp, exp2, ln, log2, sqrt, floor, ceil, round, trunc, powf, powi, mul_add` | ❌ ні — не компілюються без `std` |
| `abs, clamp, max, min` | ✅ так — компілюються й лінкуються без `std` |

### Висновок

Кламп `.min(0.225)` у `recompute_g` — **коректний і безпечний**, лишається
без змін. Але список заборонених викликів у `02_NUMERICAL_METHODS.md §7`
**сам був неточний** — ще до цього аудиту, не через мою зміну — і містив
`abs`/`clamp`/`max`/`min`, які насправді дозволені. Виправлено список;
існуючий ручний `fabs()` (бітове маскування) в коді НЕ чіпав — робочий,
протестований, міняти заради самого лише спрощення без запиту не варто.

## Реальний баг 1: DC-blocker не масштабується на `2×`

### Перевірка

`character.rs::stage()`:
```rust
let hp = y - self.dc_x1 + 0.9995 * self.dc_y1;
```
`0.9995` — «сирий» літерал, не похідний від жодного параметра рейту.
Формула `fc = (1-R)/(2π)·f_op`: при `f_op=48000`, `fc≈3.82` Гц — підтверджено
CTO. `stage()` викликається двічі на вихідний семпл у HQ-шляху
(`process_hq_pair`/`process_hq`), тобто ефективно на подвоєній частоті, а
коефіцієнт лишається тим самим → `fc` мовчки подвоюється до `~7.6` Гц.

**Це не новий баг RFC-16** — `process_hq`/`stage(x, 2.0)` існували в такому
вигляді ще до цієї сесії; RFC-19 просто вперше порівняв рейт-залежні ефекти
по всьому ланцюгу й це виявив. Стосується **обох** HQ-шляхів (standalone
`Voice` і `PolySynth`-шини), не лише нового.

### Виправлення

```rust
let dc_r = if sh_mult == 2.0 { 0.999_749_97 } else { 0.9995 };
let hp = y - self.dc_x1 + dc_r * self.dc_y1;
```
`0.999_749_97 = √0.9995` — точне співвідношення з `R = exp(-2π·fc/f_op)`:
подвоєння `f_op` вимагає `R_нове = √R_старе`, щоб `fc` лишався фіксованим.
(CTO запропонував `0.99975` — числа збігаються до 5 знаку; правильна формула
підтверджує, що це не випадковість.) Тільки два значення `sh_mult` колинебудь
передаються (`1.0`, `2.0`), тож простий `if` дешевший і безпечніший за
загальний `powf` (який і так заборонений у `no_std`).

**Тест** `character::dc_blocker_time_constant_matches_between_1x_and_2x_paths`
— порівнює загасання DC-зсуву між `process` (1×) і `process_hq_pair` (2×,
`.1`-компонент = той самий момент часу, що й одиничний вихід `process`) на
збіжних лічильниках викликів. **Перевірено, що тест реально ловить
регресію**: з незміненим `0.9995` на 2×-шляху тест падає на семплі 2000 з
розбіжністю `0.263` проти `0.097` — суттєва, не шумова різниця.

## Реальний edge-case 2: S&H без порогу bypass

### Перевірка

```rust
if self.p.downsample > 0.0 {
    let factor = (1.0 + 15.0 * self.p.downsample.min(1.0)) * sh_mult;
    self.hold_ctr += 1.0;
    if self.hold_ctr >= factor { self.hold = y; self.hold_ctr -= factor; }
    y = self.hold;
}
```
При `downsample` = мікроскопічне ненульове (наприклад, `0.0001` посеред
LFO-свіпу чи згладжування хоста через 0), `factor` трохи більший за
`sh_mult` (наприклад `1.0015`) → лічильник `hold_ctr` пропускає оновлення
**раз на ~1/(factor−sh_mult) семплів**, а не плавно наближається до
прозорого проходження. Це подія-тригер, не неперервне згасання ефекту.

### Виправлення

```rust
if self.p.downsample > 1.0e-4 {
```
Нижче порогу — повний bypass, бітова ідентичність із `downsample = 0.0`.

**Тест** `character::tiny_downsample_is_bypassed_not_jittered` — порівнює
`downsample = 9e-5` (щойно під порогом) з `downsample = 0.0` на 5000
семплах, очікуючи **побітову** рівність. **Перевірено, що тест ловить
регресію**: без порогу (`> 0.0`) тест падає точно на семплі 741 —
`0.99333906` проти `0.99383590`, відповідає розрахунковому періоду пропуску
`1/(15·9e-5) ≈ 741` семплів.

## Спростовано: пастка PolyBLEP ZOH у HQ-шині

### Теоретичний механізм — правильний, але неповний

Дублювання `(x, x)` для `Saw`/`Triangle` у `render_hq_subsamples` —
математично це «zero-order hold» апсемплінг: справді створює дзеркальний
образ спектра навколо старого Найквіста (`fs/2`) з відносно слабким
загасанням (`~-3` дБ на самому краю). Але CTO не довів це до кінця: **де**
опиняється цей образ? Через дзеркалення `f → fs − f`, вміст із діапазону
`[0, fs/2]` (стара смуга) відображається у `[fs/2, fs]` — **це територія
`2×`-шини цілком ВИЩЕ базового `1×`-Найквіста**, тобто рівно там, де й
працює майстер-дециматор, незалежно від джерела енергії (Character,
дублювання осцилятора, будь-що). Дециматор не розрізняє «легітимний» 2×-вміст
від «дублікатного» — він придушує все вище `1×`-Найквіста однаково.

### Емпірична перевірка (а не лише теорія)

Рендер `PolySynth` з `Waveform::Saw`, `CharParams::CLEAN` (щоб ізолювати
саме ефект дублювання, без плутанини від нелінійностей Character), HQ
увімк./вимк., `f0 ∈ {3, 6, 8, 10}` кГц (навмисно за межею наших власних
вимірів droop, `07 §6`, до 6 кГц):

| f0 | HQ off, найгірша поза-гармонічна | HQ on | Δ |
|---|---|---|---|
| 3 кГц | −32.0 дБ | −26.3 дБ | **+5.7 дБ** (гірше) |
| 6 кГц | −32.4 дБ | −34.8 дБ | −2.4 дБ (краще) |
| 8 кГц | −22.3 дБ | −31.8 дБ | **−9.5 дБ** (краще) |
| 10 кГц | −39.6 дБ | −39.0 дБ | +0.6 дБ (нейтрально) |

Жодної системної деградації від HQ; один випадок (3 кГц) трохи гірший,
інші — краще або нейтрально. Абсолютні числа (`−22…−40` дБ) самі по собі
низькі — але це **вже існуюча** межа PolyBLEP на екстремально високих `f0`
(за межею задокументованого діапазону `07 §6`, який зупиняється на 6 кГц),
не щось, що привносить HQ-шина. **Висновок: не критична пастка** — це
задокументована межа PolyBLEP на дуже високих нотах (`> 6` кГц), яка існує
з HQ чи без. Код НЕ змінено; вимірювальний скрипт — одноразовий, не в репо
(як `examples/fit_coeffs.rs`-подібні скрипти раніше).

## Спростовано: ADSR (1×) vs SVF (2×) «ступінчастість»

### Претензія

Фільтрова обгинаюча тикає раз на вихідний семпл (`filt_env.tick()` у
`PolySynth::render_sample_hq_bus`), встановлює ціль cutoff **один раз**, а
`Svf::process` викликається **двічі** на цей самий вихідний семпл (`lo`,
`hi`) — тож модуляційний коефіцієнт «застигає» на обидва підсемпли.

### Чому це не проблема

Це буквально те, для чого існує посемпловий згладжувач у `Svf::process`
(`04 §3.3`, задокументовано ще в `Б1`): ціль (`cutoff_t`) міняється рідше,
ніж семпли обробляються, і смузько-обмежений one-pole `cutoff_z` інтерполює
між цілями. Це не «мікроступінчастість» — це саме дизайн, що прибирає
зіпер. І важливо: у HQ-шині цей згладжувач тепер **тикає вдвічі частіше на
секунду реального часу** (бо `Svf::set_sample_rate(2fs)` коректно
перерахував `smooth` під нову частоту, RFC-16), тобто модуляція фільтра в
HQ-режимі **плавніша**, ніж у старому `1×`-шляху, не грубіша. Код без змін.

## Верифікація

62 юніт-тести (було 60, +2: `dc_blocker_time_constant_matches_between_1x_
and_2x_paths`, `tiny_downsample_is_bypassed_not_jittered`) + 5 інтеграційних
+ 1 `#[ignore]` — усі зелені. Обидва нові тести підтверджено **справді
ловлять регресію** (тимчасовий відкат фіксу → тест падає з конкретним,
очікуваним числом розбіжності). Clippy чистий (`std` + `no_std`). Біт-у-біт
на `aarch64-unknown-linux-gnu` + `armv7-unknown-linux-gnueabihf` під QEMU
(`scripts/cross-verify.sh`) — і це вкотре підтверджує, що `.min()`/`.clamp()`
не порушують крос-платформний детермінізм. Плагін збирається й лінтується
чисто; повний `pluginval`/`clap-validator` прогін не повторював — зміна
локальна до внутрішніх коефіцієнтів `Character`, не чіпає FFI, стан чи
кількість параметрів, тож попередній повний прогін (RFC-16) лишається
чинним доказом для цих поверхонь.
