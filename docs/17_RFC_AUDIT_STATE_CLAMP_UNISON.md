## Переспростовано: DC-blocker і `reset()`

### Перевірка проти реального коду (знову)

```rust
// character.rs
pub fn reset(&mut self) {
    self.dc_x1 = 0.0;
    self.dc_y1 = 0.0;
    self.hold = 0.0;
    self.hold_ctr = 0.0;
    self.decim = [0.0; HB_LEN];
}
```
```rust
// voice.rs
pub fn reset(&mut self) {
    ...
    self.character.reset();
    self.filter.reset();
    self.lfo.retrigger();
}
```
```rust
// poly.rs::trigger_one (викликається і для нового голосу, і при крадіжці)
v.core.reset(); // безумовно, останній рядок налаштування голосу перед стартом
```

`dc_x1`/`dc_y1` зануляються — не лише `hold`/`hold_ctr`. Ланцюжок
voice-stealing → `trigger_one` → `Voice::reset()` → `Character::reset()`
спрацьовує щоразу, без винятків.

**Це рівно та сама теза**, що вже перевірялась і спростовувалась у
`docs/12_TECHNICAL_SPEC_RFC.md` пункт 1.2 («S&H reset click»): «`Character::
reset()` (рядки 200–201) вже занулює `hold` + `hold_ctr` + `decim`... Витоку
немає». Різниця лише в тому, який саме стан названо (тоді — S&H, тепер —
DC-blocker) — але перевірка й висновок ідентичні: `reset()` зануляє **весь**
стан `Character`, DC-blocker включно, він ніколи не був винятком. Код не
змінювався в цій частині відтоді. Нічого не виправляв.

## Реальний баг: HQ cutoff-стеля розходиться з 1×

### Перевірка

`Svf::set_cutoff` клампив `hi = MAX_CUTOFF_FRAC * self.sample_rate`. Коли
`Svf::set_sample_rate(2×fs)` активує HQ-шину (RFC-16), `self.sample_rate`
стає робочою `2×`-ставкою — і той самий вираз дає вдвічі вищу стелю
(`0.9×fs` замість `0.45×fs`). Підтверджено: це справді означає, що
однакова LFO/envelope-модуляція cutoff відкриє фільтр удвічі далі в HQ, ніж
без нього — чутна тембральна різниця на глибоких sweep-модуляціях, не
просто «чистіше від аліасингу».

### Чому не можна просто зафіксувати кламп на старій ставці

`self.sample_rate` виконує **дві** ролі: (1) правильний prewarp
(`tan_turns_fast` у `recompute_g`) — це МУСИТЬ відображати справжню робочу
ставку, інакше фільтр рахує неправильну частоту зрізу взагалі (не лише
стелю); (2) музична стеля клампу — яка НЕ повинна плавати з робочою
ставкою. Це дві різні вимоги, що випадково жили в одному полі.

### Виправлення

Нове поле `base_sample_rate: f64` — встановлюється раз у `Svf::new()`,
**ніколи** не змінюється в `set_sample_rate` (на відміну від `sample_rate`,
яке саме для цього й існує). `set_cutoff` і повторний кламп у
`set_sample_rate` тепер рахують стелю від `base_sample_rate`; prewarp
(`recompute_g`) і час згладжувача (`smooth`) й далі рахуються від робочої
`sample_rate` — без змін, це коректно.

**Тест** `filter::cutoff_ceiling_is_identical_at_1x_and_hq_2x` — той самий
запитаний cutoff (включно з `500 000` Гц — явно за межею будь-якої стелі)
дає **точно однаковий** клампований результат при `Svf::new(fs)` і при
`Svf::new(fs)` + `set_sample_rate(2fs)`. Існуючий тест
`set_sample_rate_retargets_the_prewarp_and_the_clamp` оновлено: раніше він
очікував, що стеля РОЗШИРЮЄТЬСЯ на `2×` (стара, помилкова поведінка) —
тепер очікує, що вона лишається фіксованою на базовій ставці.

## Відхилено (з обґрунтуванням): S&H bypass не заморожує лічильник

### Претензія

Нижче порогу `1e-4` (RFC-19) блок S&H пропускається — `hold_ctr`/`hold`
лишаються «замороженими» на останньому значенні, не скидаються. При
перетині порогу назад параметр «підхоплює» застаріле значення.

### Чому не варто «виправляти» примусовим нулем

Два варіанти на перетині порогу:
1. **Заморозка (поточна поведінка).** `hold` містить останнє РЕАЛЬНЕ
   значення сигналу з моменту, коли S&H востаннє оновлювався — це не
   «сміття», а правдоподібне, обмежене за амплітудою значення. Найгірший
   випадок — до `~1-2` семплів застарілого (але не хаотичного) виводу перед
   першим новим оновленням.
2. **Примусовий нуль (пропозиція CTO).** `hold = 0.0` означало б, що при
   перетині порогу вихід миттєво падає в **тишу** на ті самі `1-2` семпли —
   це не менш помітний артефакт, а потенційно ГІРШИЙ (різкий провал у нуль
   замість плавного продовження).

Жоден з варіантів не усуває артефакт повністю — обидва обмежені 1-2
семплами при дуже специфічному, рідкісному сценарії (повільна автоматизація
`downsample` через поріг `1e-4`, значення й так нечутне на слух). Правильний
фікс (скинути `hold_ctr=0` **і** `hold = поточний_чистий_семпл` саме в
момент перетину знизу вгору) вимагав би відстежувати попереднє значення
`downsample` між викликами — новий стан заради артефакту, який і так на
межі чутності. Не варте складності. Код без змін.

## Спростовано вимірюванням: унісон при `detune=0` не перевантажує

### Претензія

`1/√n` компенсує НЕкогерентну (декорельовану) суму; при `detune=0` голоси
стають когерентними → сума росте як `n`, не `√n` → `8/√8 ≈ 2.82×` (майже
`+9` дБ) → кліпінг.

### Що насправді робить код

`poly.rs::trigger_one` (діюче незалежно від `detune`/`spread`):
```rust
if count > 1 {
    let frac = idx as f64 / count as f64;
    if !self.free_running { v.core.set_start_phase(frac); }
    ...
}
```
Кожен голос отримує стартову фазу `i/n` **завжди**, коли `count > 1` — не
лише коли `detune`/`spread` ненульові. При `detune=0` усі `n` голосів мають
**точно однакову частоту**, але **рівномірно рознесені фази** по всьому
колу (`0, 1/n, 2/n, ..., (n-1)/n` оберту). Сума `n` рівноамплітудних
синусоїд з фазами `2πi/n` — тотожний нуль для `n≥2` (класична тотожність
коренів з одиниці). Для гармонічного (не чисто синусоїдального) сигналу
кожна гармоніка `k` гаситься по-своєму (гармоніки, кратні `n`, гасяться
менше — там усі голоси фазово збігаються), але системного підсилення немає
ніде.

### Виміряно (`unison 8`, `1/√8` компенсація, пік проти одного голосу)

| `rolloff` | `detune=0, spread=0` |
|---|---|
| `0.0` (майже синус) | **`0.000×`** — повна тиша |
| `0.5` | `0.013×` |
| `0.9` (яскраво) | `0.270×` |

Ніде немає навіть натяку на `2.82×`. Реальний ефект — **протилежний**:
занадто тихо, аж до повної тиші на бідному гармоніками сигналі, не
перевантаження. Задокументовано в `07_LIMITATIONS.md §13`. Код без змін —
це очікувана поведінка дизайну фазової декореляції, не баг; `detune=0` —
вироджений, нетиповий випадок для ручки, чиє призначення — розстроювання.
