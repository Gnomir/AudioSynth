## Правильно: гребінчаста фільтрація при `detune=0`

Алгебраїчно точно (перевірено, узгоджується з виміряними `0.270×`/`0.013×`/
`0.000×` з попереднього раунду): стартова фаза `i/n` зсуває `k`-ту гармоніку
на `k·i/n` обертів; сума `n` фазорів `Σᵢ e^{i2πki/n}` — геометричний ряд, що
дорівнює `n` при `k ≡ 0 (mod n)` і `0` інакше. Унісон при `detune=0` —
буквально гребінчастий фільтр з кроком `n` (виживають гармоніки `n, 2n,
3n…`). Для `rolloff→0` (уся енергія в 1-й гармоніці, `1 ≢ 0 mod 8`) —
точний нуль; для `rolloff=0.9` виживають 8-ма/16-та/… гармоніки — звідси
ненульові `0.270×`. Додано в `07_LIMITATIONS.md §13` як точну форму
(раніше там була лише якісна згадка «гаситься по-своєму»).

## Хибно (повторно): `drift_phase` не wrap'иться

### Претензія

Без примусового обгортання `drift_phase` накопичується безмежно; за дні
роботи перевищить `10⁷`, редукція аргументу `turns - round_int(turns)`
почне втрачати молодші розряди мантиси `f64`.

### Реальний код (`voice.rs`, усередині `tick_modulation`)

```rust
let drift = if self.drift_depth != 0.0 {
    self.drift_phase += self.drift_inc;
    if self.drift_phase >= 1.0 {
        self.drift_phase -= 1.0;
    }
    self.drift_depth * sin_turns_fast(self.drift_phase)
} else {
    0.0
};
```

Це **точно** та конструкція, яку пропонує ТЗ як фікс (`+= inc; if >= 1.0
{ -= 1.0 }`) — вона вже там, ідентична до того, як `self.phase` (несуча) і
`self.fm_phase` самі себе обгортають. `drift_phase` ніколи не виходить за
`[0, 1 + drift_inc)` — не існує сценарію, де воно сягне навіть `2.0`, не
кажучи вже про `10⁷`. Жодної втрати точності мантиси немає й не може бути.
Код не змінювався.

## Хибно (подвійно): `sample_rate = 0` при ігноруванні `initialize → false`

### Половина 1: обчислення захищені незалежно від того, що повертає `initialize`

```rust
// lib.rs
pub fn validate_sample_rate(hz: f64) -> (f64, SampleRateStatus) {
    if !hz.is_finite() { (48_000.0, SampleRateStatus::Defaulted) }
    else if hz < SAMPLE_RATE_MIN { (SAMPLE_RATE_MIN, SampleRateStatus::ClampedLow) }
    else if hz > SAMPLE_RATE_MAX { (SAMPLE_RATE_MAX, SampleRateStatus::ClampedHigh) }
    else { (hz, SampleRateStatus::Ok) }
}
```

`Voice::new`/`new_checked` і `PolySynth::new`/`new_checked`/`set_sample_rate`
**завжди** проходять через це — немає жодного конструктора, що приймає
сирий, неперевірений `f64`. `0.0.is_finite() == true`, тож `0.0` не тікає
крізь перший `if`; воно ловиться другим (`< SAMPLE_RATE_MIN`) і клампиться
до `8000.0`. `NaN`/`±Inf` ловляться першим. **Ділення на нуль чи NaN у
`freq/sample_rate` структурно неможливе** — не питання того, чи хост
поважає `initialize`, воно неможливе на рівні конструктора незалежно від
того, хто й коли його викликає.

### Половина 2: плагін давно не повертає `false`

```rust
// harmonic_synth/src/lib.rs::initialize
// Clamp + warn, but keep running — a host that hands us an odd rate
// (pluginval tries 1234 Hz) should still get audio, not a rejected activate.
let status = self.engine.set_sample_rate(buffer_config.sample_rate as f64);
if status != harmonic_core::SampleRateStatus::Ok { nih_log!(...); }
...
true
```

`initialize` **завжди** повертає `true` — сама передумова «якщо хост
проігнорує false» не застосовна, бо `false` ніколи не повертається. Обидві
половини претензії розходяться з реальним, поточним кодом; можливо, опис
описував попередню, давнішу поведінку плагіна (яка справді відхиляла
ініціалізацію на не-`Ok` статус) — але це вже не так, і повідомлення про
проблему мало б спиратись на код, що є, а не на пам'ять про версію, яка
давно змінилась.

## Реальне, задокументоване: клацання при voice-stealing

Див. `07_LIMITATIONS.md §14` для повного опису. Коротко: 16-семпловий
`declick` захищає лише fade-**in** нової ноти; коли крадеться **активний**
голос, його попередній рівень (будь-яка амплітуда) обривається за 1 семпл
до `≈0.06×` нового осцилятора — короткий, широкосмуговий транзиєнт. Свідома
плата за компактний (512 б) POD `Voice` без місця для одночасного
fade-out/fade-in у слоті. Не виправлено — задокументовано.
